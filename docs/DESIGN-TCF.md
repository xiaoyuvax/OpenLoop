# 设计：TCF —— TargetCentricFacility（左栏文本编辑器与目标工具架构）

> 状态：**架构定稿（2026-11-24，用户给出设计要求）**；实现尚未开始，现状见 §8。
> 目标读者：实现者；也用于判断改动是否越界。

## 1. 定性

**TCF（TargetCentricFacility）= 面向用户的文本多轮可视化编辑交互工具类型**：
从跟用户的视觉交互过程中获取数据，对**某一个数据对象**做多轮次的「雕塑性」修改
（每轮看效果、再改，直到用户满意）。

- 性质类似内建 Tool，但不走工具调用的「请求→结果」形态：它有持久可见的界面，
  数据在多轮之间驻留。
- **不是常设工具**：TCF 内建于壳、只有壳支持时才能启用，且只用于特定任务；
  不进默认提示词/工具表（为精简提示词）。启用方式是宿主消息按需告知。
- 现有实例：会话左栏的编辑目标面板（`TargetPane`，TargetCentricSession 的编辑面，
  prompt / agents 两种 Kind）。以后引入面向其他类型文件的编辑器
  （svg / gltf / 网页等）= 新 Kind + 新呈现控件 + Bind，不改会话主流程
  （沿用 `TargetSpec` 的扩展约定）。

### 1.1 与 LoopApp（OpenUI）的关系

TCF 与 LoopApp 不是能力互斥，而是**可见性与启用时机**不同：

| | TCF（目标编辑面） | LoopApp（OpenUI） |
|---|---|---|
| 定性 | 壳内建宿主控件，对同一数据对象**多轮雕塑性编辑** | agent 即时生成的可视化交互页面（**通常用于一次性任务**） |
| 数据 | 会话绑定的目标文件（prompts/system.md、AGENTS.md，以后可扩） | `.openloop/tmp/LoopApps/<slug>/` 下的自包含应用 |
| agent 操作通道 | Puppet A/B 面直接操作壳内控件本体 | 改文件 + `LoopApp(eval/reload)`，页面经 `ui.submit` 回消息 |
| agent 如何知道它 | **只有宿主消息显式启用后才知道**；不进提示词、不进常设工具表 | openui 技能常设，agent 随时可用 |
| 生命周期 | 跟随会话目标模式，关闭=隐藏、内容驻留内存直到保存或放弃 | 任务做完收起，闲置销毁 |
| 典型场景 | 「把这段提示词第 3 节改紧一点，我看着你改」 | 表单收集、看板、向导等一次性交互 |

要点：

- TCF 不随系统提示词注入，**未启用时 agent 不知道它存在**——这种情况下
  LoopApp 完全可以承担多轮雕塑性任务，没有限制。
- **一次性可视化交互建议 agent 走 openui 技能（LoopApp）实现**；
  LoopApp 通常用于一次性任务，但这只是建议，不是能力边界。
- 只有宿主消息启用了 TCF（告知文件路径与操作接口）时，编辑该目标才交给 TCF，
  不另起 LoopApp 抢场景。openui 技能正文里已按这条写（`src/OpenUI/skills/openui/SKILL.md`）。

## 2. 数据填充：两种模式

TCF 的数据可以由两条路径进入编辑器：

1. **壳预填充 + 宿主消息告知**：壳把文件加载进编辑器，然后以**宿主临时插入的消息**
   （宿主消息类型）告知 agent：已加载文件的路径、编辑器的操作接口指南。
   agent 不需要自己查询控件状态，消息里直接给。
2. **宿主告知用法，agent 自行填充**：宿主消息只给 TCF 的使用方法（属性 + Action 清单），
   由 agent 自己调加载接口把文件填进去再操作。

两种模式共用同一套操作接口（§3）；宿主消息是 agent 认识 TCF 的唯一入口——
TCF 不进常设工具表，也不进系统提示词。

## 3. Agent 操作通道：Puppet A/B 面

TCF 位于壳内，agent 操作一律走 **Puppet 的 A/B 面**（与 AGENTS.md「只用 Puppet 调试」的
既有约定同一条路，不走 UI 自动化）：

- **状态 = 公共属性**：为 TCF 设计专用的公共属性暴露必要状态与属性，
  例如：文本长度、行数、脏标志（有无未保存修改）、保存目标路径、当前光标/选区等。
  A 面 `/agent/get` 直接可读。
- **操作 = 专用 Action**（`[PuppetAction]`，B 面 `/appagent/*` 具名动作），
  按编辑语义设计成**高效、少往返**的粒度：
  - 按区段读取（行号区间 / 偏移区间）
  - 按区段替换（旧行区间 → 新文本）
  - 按位置插入 / 删除
  - 尾部追加
  - 撤回（undo）
  - 保存（§4 语义）
- **宿主消息直接提供属性名与接口指南**，agent 无需先探测 manifest 再猜参数。

这套「壳内控件 = Puppet 属性 + Action」是架构基础：以后壳里任何要给 agent 操作的
宿主控件（不限于文本编辑器）都按这个范式暴露，不再各写一套通道。

## 4. 编辑与保存语义

- **所有编辑发生在壳进程的内存内**：agent 的编辑 Action 只改内存缓冲区，
  实时反映在编辑器窗口供用户查看。
- **用户未确认前不得保存**：落盘必须经用户确认（审批或显式确认动作）。
- **关闭 = 隐藏**：关闭编辑器只是隐藏面板，内容驻留内存直到保存或用户确认放弃。
- 关闭/隐藏时若有未保存内容，壳**通知 agent**，由 agent 询问用户「保存还是放弃」，
  按答复执行：保存 = 落盘；放弃 = 丢弃内存缓冲。

## 5. 界面要求

- **保存目标路径**：不必持续展现；放在 tooltip 中，用户按需查询（悬停可见）。
- **保存状态**：图标 + 色彩展现（如：已保存=绿色勾、有未保存修改=橙色圆点、
  落盘失败=红色叉）；**复用保存按钮**，不另加状态栏。
- **现有按钮图标化**：编辑面板的工具栏按钮一律用图标（带 tooltip），
  减少多语种版本（Localization）的维护负担。
- 颜色从 `UiStyle` 取，不写死 `Color.X`（既有 UI 规则）。

## 6. 与 TargetCentricSession 的关系

- **TargetCentricSession（TCS）是会话模式**：绑定一个唯一编辑目标、聊天驱动模型落盘。
- **TCF 是这类工具的统称与扩展架构**：TCS 的 TargetPane 是 TCF 的第一个实例；
  「agent 可通过 Puppet 操作编辑器本体」是 TCF 对 TCS 现状的增强方向
  （现状面板只读，改动只能由模型经文件工具落盘、watcher 刷新）。
- 两条数据流并存：模型经 WriteFile 落盘 → watcher 刷新（现状）；
  agent 经 Puppet Action 编辑内存缓冲 → 用户确认落盘（本设计）。
  二者不冲突：落盘后的文件内容仍是权威态，内存缓冲是待确认的工作态。

## 7. 提示词成本

TCF 不进系统提示词、不进常设工具表——**未启用时 agent 不知道它存在**。
agent 对 TCF 的全部认知来自宿主消息（含文件路径、属性清单、Action 用法、
保存语义的一句话约束）。`AGENTS.md` 只保留一句定性（见该文件 TargetCentricSession 条目）。

## 8. 现状与实现顺序

现状（已存在）：
- `src/OpenLoop.App/TargetPane.cs` / `TargetPane.Designer.cs`：只读呈现 + watcher 刷新，
  按钮是文字（「独立窗口」「关闭」），无保存语义、无 Puppet 属性/Action。
- `src/OpenUI/skills/openui/SKILL.md`：有 LoopApp 决策表与 TCF 区分说明（已补）。

实现顺序建议：
1. TargetPane 编辑化：可编辑 FCTB + 内存缓冲 + 脏标志 + 保存/放弃确认流。
2. 按钮图标化 + 保存状态图标 + 路径 tooltip（§5）。
3. Puppet 属性 + Action（§3），A/B 两面同源。
4. 宿主消息协议（§2）：两种填充模式的消息文案模板。
5. 关闭时未保存内容的通知链路（§4）。

验收：
- agent 收到宿主消息后，不开新工具、不读文档，直接经 Puppet 完成一段替换编辑，
  界面实时可见；落盘前用户确认弹问；未保存关闭时 agent 收到通知并能询问用户。
- 提示词无 TCF 内容；会话无目标绑定时面板不出现。
